# Задача 1.1

## Вопрос 1. Почему `ProcessDamage` принимает `List<IDamageable>`, а не `List<Player>` или `List<Trap>`?

Потому что `GameSystem` нужно наносить урон всем, кто умеет его получать, а не только игроку или только ловушке. Если написать `List<Player>`, то ловушки в такой список положить нельзя, и для них пришлось бы писать отдельный метод. А для каждого нового класса (например, врага или бочки) пришлось бы писать ещё один. Интерфейс `IDamageable` говорит, что у объекта точно есть `TakeDamage` и `HP`, и методу этого достаточно. Это и есть полиморфизм: в один список можно положить и `Player`, и `Trap`, а при вызове `target.TakeDamage(damage)` выполнится метод того класса, которым объект является на самом деле. Поэтому при добавлении нового класса, который реализует `IDamageable`, код `GameSystem` менять не придётся. Метод зависит от интерфейса, а не от конкретных классов, и это удобно.

## Вопрос 2. Является ли нарушением контракта то, что `Trap.TakeDamage` возвращает `false` и не меняет HP?

Для компилятора это не нарушение: метод с нужной сигнатурой есть, значит, интерфейс реализован. Но по смыслу выходит странно. У `Player` значение `bool` означает «объект ещё жив после удара» (`_hp > 0`). А `Trap` всегда возвращает `false`, то есть как будто «умерла», при этом её `HP` всё время равно 10, потому что сеттер пустой. Вызывающий код видит HP = 10, но получает ответ «не жива», и это противоречит друг другу. Ещё при каждом повторном ударе снова выводится «Ловушка разбилась!», хотя она уже разбита. Если задумано, что ловушка ломается с одного удара, то это нормально, но тогда после удара HP должен стать 0. Поэтому, на мой взгляд, прямого нарушения нет, но для вызывающего кода это «странно», и лучше так не делать.

## Вопрос 3. Что было бы, если бы зелье пытались лечить через `ProcessDamage`?

`HealthPotion` реализует только `IHealable`, а `ProcessDamage` принимает список `IDamageable`. Поэтому зелье в такой список просто не добавить: программа не скомпилируется, и компилятор покажет ошибку ещё до запуска. Это хорошо, потому что ошибка находится сразу, а не во время игры. Если бы мы попробовали обойти это приведением типа `(IDamageable)potion`, то при запуске программа упала бы с ошибкой `InvalidCastException`. А если бы мы заставили зелье реализовать `IDamageable`, то получилась бы путаница: зелье «получало бы урон», у него появились бы ненужные HP, а лечения не было бы вообще. Поэтому у нас два разных интерфейса и два разных метода: один для урона, другой для лечения.

## Вопрос 4.
Придётся изменить все классы, которые реализуют `IDamageable`. В примере это `Player` и `Trap`. `HealthPotion` менять не надо, потому что он реализует только `IHealable`. Если этого не сделать, проект не соберётся: компилятор напишет, что класс не реализует член интерфейса `IsDead`. Интерфейс — это контракт, и каждый класс, который его реализует, обязан выполнить его целиком (принцип контракта). Для `Player` можно написать `IsDead => _hp <= 0`. Для `Trap` свойство нужно сделать согласованным с `TakeDamage`: после удара ловушка разбита, значит, `IsDead` должно быть `true`. Если просто написать `IsDead => false` для заглушки, то компилятор успокоится, но логика сломается: `TakeDamage` скажет, что объект уничтожен, а `IsDead` скажет, что он жив. Поэтому интерфейс лучше продумывать заранее, чтобы потом не менять все классы.

# Задача 1.2

Может содержать поля с конкретными значениями | + | − | В абстрактном классе можно объявить обычные поля и задать им значения. В интерфейсе полей экземпляра нет, он описывает только поведение.
Может иметь полноценный конструктор | + | − | Конструктор абстрактного класса вызывается из конструкторов наследников. У интерфейса конструкторов нет.
Один класс может наследовать/реализовывать несколько таких типов | − | + | Базовый класс у класса может быть только один, а интерфейсов можно реализовать сколько угодно.
Может содержать реализацию метода по умолчанию | + | − | В абстрактном классе обычные методы с телом разрешены. В интерфейсе по классическим правилам метод только объявляется, а тело пишет класс. (В новых версиях C# с 8.0 есть реализация по умолчанию, но по лекции интерфейс описывает только контракт.)
Может объявлять свойства без реализации | + | + | В абстрактном классе это `abstract`-свойство, в интерфейсе свойство без тела (`int HP { get; set; }`).
Может быть использован как тип поля или переменной | + | + | Переменной такого типа можно присвоить объект любого наследника или реализации. Создать объект через `new` нельзя, а использовать как тип можно.
Может наследовать классы | + | − | Абстрактный класс может быть наследником другого класса. Интерфейс может наследоваться только от других интерфейсов.
Может содержать приватные методы | + | − | В абстрактном классе `private`-методы есть как в обычном. Интерфейс описывает то, что видно снаружи, поэтому приватные методы ему не нужны (в C# 8.0 их добавили, но только как вспомогательные).
